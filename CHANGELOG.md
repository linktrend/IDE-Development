# Changelog

## v3.0.0 — 2026-09-29

Wave 1 of v3: IDE Development becomes the shared development operating System (Program-ready).

### Operating model

- One AI orchestrator per repo: a Cursor Project on the cursor-001 account running a frontier model. It plans Phases and Issues, dispatches Issues, packages branches into pull requests into `development`, merges on green CI plus one independent review, and promotes `development` to `main`. Cheap helper subagents do routine jobs (packaged cheap-helper rule)
- Workers: Codex CLI on the orchestrator VM (Luna High everyday, Sol Medium hard; used while more than 25% allowance remains in every reported window) and the cursor-002 account via API (Grok 4.7 Medium everyday, Opus 5.5 Medium hard)
- Workers use `issue/<PREFIX>-<n>-<slug>` branches named from Ledger IDs, commit and push often, run fast checks, end with a lessons note, and never open pull requests
- Checks: fast checks per branch, one Full CI run per pull request (`Verify IDE Development`), one exact-head review by a different model family (Bugbot optional)
- Repair ladder: Luna/Grok three times, then Sol/Opus once, then (if the work started on Sol/Opus) the other hard route once, then flag Carlos
- Ledger: Supabase schema `ide_ledger` in the LiNKplatform project, written only by the orchestrator via RPC. Until it is live, the pilot run log stays in the Project store. IDs `IDE-<n>`. One GitHub Issue per Phase is the readable summary
- Carlos gives intent and answers questions; he does not approve merges or releases

### Routing

- v3 routing registry, contract, skill and PRD; cursor-002 Grok 4.7 and Opus 5.5 dispatch pinned; unknown cursor-002 routes and aliases fail closed

### Release policy and branch model

- Long-lived branches are `development` and `main` only; `staging` is removed from branch logic, gitops modules, schemas, cleanup and protections
- Pull requests into `development` come from work branches; into `main` only from `promote/main/*`
- `main` promotion is orchestrator-owned and checked by `Linktrend Receipt Gate` (legacy name): the promoted tree must equal a `development` commit, pushed on `development`, whose `Verify IDE Development` passed
- Deploys after `main` are automatic GitHub Actions jobs with a health check and rollback; the standard is owned by the LiNKops repo

### Orchestrator scripts

- `scripts/orchestrator/`: `package.py` (merge worker branches into `phase/<slug>` without resolving conflicts), `merge_check.py` (exact reviewed head, green checks, clean merge), `promote_main.py`, `promotion_check.py`, run log and watchdog; shipped in the managed runtime; runbook `docs/runbooks/orchestrator-delivery.md`

### Removed

- Staging; Mac Mini coordinator; Lisa ship/pull waves and repair dispatcher; Review Ready publisher; completion-gate evidence; review-gate classifier; repair observer; promotion receipts and receipt seal; packager and delivery controller; Cursor Automations docs
- Hand-copied skills (replaced by a pinned LiNKskills sync, `scripts/sync-linkskills.py`)

### Installer upgrade (v2.5.2 → v3.0.0)

- `ide-development.py update` deletes the 62 managed files v2.5.2 shipped and v3 retired, by exact v2.5.2 hash, from migrations generated by `scripts/ide_development/v3_retirements.py`
- The same transaction deletes the v2 root workflows in consumer `.github/workflows/` when they equal a published v2 rendering (`scripts/ide_development/retired_workflows.py`); `scripts/sync-managed-workflows.sh` and `backfill-managed-workflows.sh` apply the same hash guard
- A locally modified retired file is a conflict with a clear message, never deleted; `rollback` restores exact bytes and modes; `verify`/`drift` report no orphans after the upgrade
- Managed runtime text (AGENTS section, Cursor bootstrap and branching rules) describes v3, and `build_manifest --verify` keeps every copy identical to its source
- Package, installer and release-publisher identity is 3.0.0; the v2.5.2 same-version repair and the OpenClaw admission contract keep recognising 2.5.2
- Proof: `scripts/ide_development_tests/test_v3_upgrade.py`; runbook `docs/runbooks/v3-upgrade.md`

### Deploy caller

- `core/github/managed-workflows/linktrend-deploy.yml` (`Linktrend Deploy`) calls `linktrend/LiNKops/.github/workflows/deploy.yml@v1`; synced only into repos with `deploy/target.json`; interface in `docs/contracts/DEPLOY-CALLER.md` (proposed; LiNKops confirms in its Wave 2.3)
